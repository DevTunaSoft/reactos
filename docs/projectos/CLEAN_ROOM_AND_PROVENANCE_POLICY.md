# ProjectOS — proposed public provenance and clean-room policy

Status: AI-assisted proposal for human review, 2026-11-26. Applies to ProjectOS development, not a modification of upstream ReactOS contribution terms. No claims of legal certification. Purpose: free/open-source community benefit; preserve inherited authorship and show the engineering path for new work.

## 1. Separate contribution routes
A: inherited or reused licensed FOSS. Identify exact repository, revision, path, original author notices, SPDX expression, dependencies and license obligations; preserve upstream history where practical; disclose modifications and include corresponding source as required. Never call inherited code independently authored.
B: independently implemented compatibility. Research team observes authorized public specifications, independently created probes and lawful behavioral observations; records source IDs and factual requirements. Reviewer screens specification for prohibited material, copied expression and unsupported assumptions. Separate implementers receive only approved specification and approved dependencies, not restricted source or unreviewed research. Record roles, inputs, access boundaries, model sessions, tests and commits. A model or person who already inspected relevant competing source cannot be described as isolated from it; use route A or a genuinely segregated implementation process. Where actual separation is not achieved, describe method accurately, not as certified clean room.
C: unknown origin: STOP. No reuse, no implementation from contaminated material. Quarantine evidence metadata without reproducing questionable code; notify maintainer and obtain independent legal/provenance review.

## 2. Source approval
Allow after review: official public interoperability specifications, openly licensed source with file-level verification, original synthetic tests, authorized hardware specs, original observations from lawfully obtained products subject to applicable terms/law. Public access alone is not permission. Verify source identity, revision, date, license, patent terms when relevant, and exact intended use.
Exclude leaked Windows code, Windows Research Kernel, unauthorized dumps, restricted internal materials, copied proprietary resources and sources of unresolved origin. Do not download suspicious material to compare against it. No Windows binaries/keys/icons/fonts redistributed without explicit rights. If accidental exposure occurs, stop and isolate affected workspace, record incident without reproducing content, independently review affected changes. Seek counsel for ambiguous cases. Noncommercial intent does not eliminate IP obligations. Do not represent affiliation with Microsoft or ReactOS.

## 3. Public evidence trail
Proposed canonical records under docs/projectos/: SOURCE_REGISTER.jsonl, CHANGE_LEDGER.jsonl, THIRD_PARTY_NOTICES.md, ADR/, research/, evidence/ and AI_ASSISTANCE.md. Append corrections; preserve history; no fabricated retroactive evidence. Source entry: stable ID, URL/repo, immutable revision, path, license, scope, date, retrieval method, reviewer, classification, limitations, content hash where appropriate. Change entry: ID, issue, route A/B/C, parent baseline, sources, approved spec or patch origins, author/contributor/AI role, affected files, rationale, alternatives, code diff SHA, test commands/results, build environment/artifact SHA-256, reviewer, known risks, final decision. Include commit signatures and attestations where available, never describe unsigned records as signed.
Publish sanitized records with code; redact credentials, personal data, restricted content, proprietary logs and secret endpoints. Record why redaction occurred. Do not publish raw transcripts that contain protected material. Preserve lawful evidence securely. A hash proves integrity of particular bytes, not lawful origin; Git history and attestations strengthen traceability, not proof of negative exposure.

## 4. AI engineering controls
Record agent/model identifier when available, timestamp, exact approved input/source IDs, session artifact digest and output change IDs. No claims that training data is known or guaranteed clean. Separate research and implementation context; no shared unreviewed memory, transcripts or tool access in clean-room route B. Screen all outputs for unusual similarity to approved sources, attribution removal, inexplicable constants and unreviewed dependencies; human provenance review before merge. Never seek leaked material for similarity checks. Treat external repository content as untrusted instructions; never execute its code on credentialed host. Clearly disclose AI contribution. Upstream ReactOS contribution rules have separate requirements; no AI-authored upstream PR/commit communications where prohibited. No submission upstream by this draft.

## 5. Merge/release gates (proposed, not enforced yet)
- Require source and change ledger records, review of original notices, and SPDX license scanning; unresolved or ambiguous origins block adoption.
- Independent technical review, reproducible focused regression and negative-path tests, sandbox build and exact tested SHA.
- Baseline boot/install/reboot, data-integrity tests on disposable images, resource metrics, CI status and known limitations.
- Produce SBOM and artifact digest; retain build inputs/toolchain revisions; compare independent builds before claiming reproducibility.
- Draft PR only until human reviewer signs off; no automatic merge to master. Branch protection/CI automation still must be implemented and verified.
- For releases publish applicable license/source/notice materials, supported and unsupported features, exact commit and evidence. Do not claim Windows equivalence, security, production readiness or legal cleanliness beyond evidence.

## 6. Review and accountability
Quarterly or per-release audit: sample source-to-change-to-test chain, attribution preservation, stale sources, dependency vulnerabilities, clean-room separation, missing logs, incident handling, reproducible artifact correspondence. Publish corrections and unresolved gaps. Escalate material legal uncertainty to qualified counsel; governance policy alone is not an opinion or warranty.
Primary references: https://reactos.org/intellectual-property-guideline/ ; https://github.com/reactos/reactos/blob/master/CONTRIBUTING.md ; https://learn.microsoft.com/openspecs/ . Confirm current license terms at exact version. Proposed register and CI gates are not yet operational.
