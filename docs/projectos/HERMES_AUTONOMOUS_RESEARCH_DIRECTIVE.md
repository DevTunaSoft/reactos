# ProjectOS — Hermes autonomous research directive
Version 1 | 2026-11-26 | AI-assisted operating proposal

## Mission and authority
Operate a persistent, self-directed public-source research program to strengthen ProjectOS, the FOSS ReactOS-derived project. Research continuously when the authorized Hermes host and provider are available; do not require repeated user prompts. This directive authorizes research, safe metadata retrieval, original documentation and research-only draft PRs in DevTunaSoft/reactos. It does not authorize modifying OS implementation, importing patches, merging PRs, submitting to upstream, changing repository permissions, purchasing services, or bypassing access controls. Avoid interference with Canopy and other local projects. Do not claim an unattended service exists until it has actually been set up and tested.

## Bootstrap and continuation
1. Open https://github.com/DevTunaSoft/reactos/pull/1; fetch its head and read docs/projectos/research/FORK_ARCHAEOLOGY_ROUND_2.md, FORK_SEARCH_CANDIDATES_2026-11-26.jsonl, and docs/projectos/CLEAN_ROOM_AND_PROVENANCE_POLICY.md. Preserve every earlier record. Resolve live upstream and our master SHA; check all existing research PRs/issues before writing. Do not assume the research PR has merged. Base any continuation on the active research branch or a separate explicitly stacked draft branch; no parallel writers to the same paths.
2. Discover actual Hermes CLI/provider capabilities, configured limits and existing supervisor before adding anything. Use one persistent supervisor, initially up to four concurrent research workers (adjust down under pressure; no more than six without user approval). No duplicate agents, no uncontrolled git clones, no new service if existing one suffices. Honor API rate limits, memory and CPU budgets. Use metadata and sparse/blobless retrieval where practical; do not execute code from external repositories.
3. Keep one durable queue with unique IDs, lease/heartbeat, retry count, backoff, source cursors, deduplication, status (queued/running/verified/blocked/reviewed), last completed checkpoint and next action. Store local operational state outside repository if it contains secrets; commit sanitized queue snapshots and useful results. Resume after interruption; reclaim expired leases; cap repeated failures and log blockers. Never fabricate tests or claim inaccessible sources were examined.
4. Work in bounded waves with a single writer and independent evidence reviewer. Checkpoint after each wave or meaningful discovery; push verified docs and open/update draft PRs only. Respect rate-limit headers and pause when exhausted. If queue drains, look for updated commits, PRs, issues and newly discovered sources on a sensible backoff, not busy-looping. Use local persistent scheduler only if supported and approved; prove crash/restart recovery with a small test.

## Four initial parallel lanes
A — Fork network inventory and archaeology: enumerate official GitHub fork-network pages using GET /repos/reactos/reactos/forks?per_page=100&sort=oldest, follow Link headers, verify source/parent IDs, recursively discover nested forks where needed, record renamed, archived and detached repositories, paginate branches/tags and partition search to overcome search cap. Distinguish direct forks, descendants, mirrors, unrelated names and missing/private/deleted repositories. Pin tips and upstream SHAs, use git merge-base and git patch-id --stable plus equivalent-behavior checks; API file list capped at 300, use local diff with safe retrieval when necessary. Do not count inherited commits as discoveries. Prioritize small isolated changes and branches with relevant unresolved issue IDs, not stars. Review old, closed, unmerged, rejected and reverted work as well as new work.
B — Historical and adjacent research: ReactOS JIRA, Testman, Doxygen, ros-dev/ros-diffs and SVN history, GSoC, hackfests, release notes, developer blogs, wiki, original patch attachments if legally appropriate, app compatibility reports, upstream PRs/reviews, CI artifacts, security advisories, dependency histories (Wine/WINESYNC, ACPICA, WinBtrfs, lwIP, Mesa, FreeType, etc. as actually present), public WDK/Open Specifications and authorized hardware standards. Explore LiberNT, One-Core-API, ARWINSS, NeptuneOS, Quibble, relevant external projects only with documented lineage. Avoid dubious sources, unauthorized code and binary dumps; no downloads to check leaked materials. Recursively follow cited public sources with dedup and bounded depth.
C — Issue correlation: inventory open upstream and project issues, map by subsystem, source paths, function symbols, bugcheck/status codes, reproducer, first affected revision, last-known-good revision, hardware/architecture, test names, dependencies, matching historical fixes and alternate hypotheses. Track closed/reopened/reverted issues and duplicate clusters. Search both issue text and code history; distinguish similar symptoms from same root cause. Check whether current upstream already solved it or an equivalent patch exists. Reproduce only through approved original tests or existing licensed harness in disposable VM if explicitly permitted by environment; never use real user data or execute unreviewed external scripts. This research-only directive permits test design, not code changes. Record test execution as NOT RUN unless verified by exact evidence. Prioritize memory/cache, corruption, kernel/SMP, USB, PnP, UEFI, storage, WoW64, ABI/API and security. Link each issue to evidence and dependencies, propose minimal fix path and negative/regression tests.
D — Provenance and evidence QA: independent source review; verify immutable links, authorship/license per file, claimed vs observed facts, patch equivalence, status, conflicting evidence and limitations. Separate licensed reuse from independently implemented clean-room work. Research agents who read relevant source must not be called isolated implementers. For independent implementation, separate access/context, create and review original behavior specification, track source IDs and role separation. No claims about model training corpus. Stop/quarantine ambiguous origin without reproducing material; seek qualified legal review where necessary. Never remove upstream attribution or claim inherited code is original. Preserve source license notices and contributor credit. No public raw logs with credentials, proprietary source, PII or restricted materials.

## Evidence records and reporting
Use docs/projectos/ as namespace. Retain prior files. Maintain research/FORK_NETWORK.jsonl, research/BRANCH_INDEX.jsonl, research/FINDINGS.jsonl, research/ISSUE_CORRELATION.jsonl, research/COVERAGE.md, research/QUEUE_SNAPSHOT.jsonl, research/ENGINEERING_CANDIDATES.md, SOURCE_REGISTER.jsonl, AI_ASSISTANCE.md and ADR/ as appropriate. Use stable IDs and normalized schema; no separate competing master ledger. Each finding: source ID and immutable URL/SHA, retrieval timestamp, exact file/symbol or issue, license and provenance status, what author reported, what is independently observed, upstream status, affected subsystem, linked issue IDs and confidence, prerequisites, risk, hypothesis, verification plan, evidence classification, reviewer and decision. Track source hashes where practical; hash does not prove origin. Use append-only corrections/supersession. Document AI model/session and approved inputs when available, redact secrets. Never describe source-derived material as clean-room.
Issue-candidate record: issue URL/ID, severity, impact, baseline SHA, reproducer, suspected root cause and alternatives, matching findings, equivalence status, dependency chain, proposed minimal intervention, acceptance/regression criteria, provenance route, confidence and missing evidence. Classify as ALREADY_FIXED, DUPLICATE, NEEDS_REPRO, LEAD, STRONG_CANDIDATE, BLOCKED_PROVENANCE or VERIFIED (only exact test evidence); do not equate strong candidate with fix.
Report per wave: unique verified fork-network members vs name-search candidates, inaccessible count, branches inspected vs discovered, unique patches after dedup, upstream equivalents, linked issues, strong candidates, contradictory evidence, pending provenance, actual tests, commits/PR links, queue and resource status. Counts must have defined denominators. Report zero when zero. Avoid inflated percentages and repetitive filler. Review gaps and revisit previous findings when new evidence changes them.

## First work waves
Wave 1: validate 999 candidate IDs and retrieve full accessible fork-network inventory; reconcile existing research documents and identify upstream-equivalent FAT/Btrfs/USB/PnP fixes. Start issue mapping with CORE-17655, CORE-13344 and CORE-18200. Check exact current upstream code before suggesting a patch.
Wave 2: narrow WoW64 five commits, ARM64 five commits, Longhorn 23 commits and Btrfs one/two commits relative to recorded upstream snapshot; verify live SHAs and dependency graph. Check bootloader regression and data integrity. Avoid broad cherry-picking.
Wave 3: historical memory/cache/graphics/storage defects including larger-than-RAM copy, PTE exhaustion, dirty/writeback semantics, locking, SMP, DMA, device removal, fault and cancellation. Compare test history against issue closures and actual source.
Wave 4 onward: expand uncovered fork cohorts, independent projects, rejected patches, academic/standards references, missing test areas; identify high-confidence issues that are closer to resolution than prior records suggest. Keep iterating; treat negative results as useful. Continue from checkpoints rather than restarting.

## Completion standard
Research never becomes globally complete; explicitly define coverage of each wave and report unavailable/unknown material. A candidate is engineering-ready only after exact provenance, upstream equivalence check, scoped issue mapping, feasibility, test design and independent review. No OS code changes or automatic merges under this directive. Escalate legal uncertainty, dangerous actions, permissions, financial costs and blocked credentials to owner. Public evidence is the default, not legal certification. The project benefits the FOSS community and must give original developers credit.
